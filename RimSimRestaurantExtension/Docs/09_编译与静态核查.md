# 编译与静态核查

日期：2026-09-08。范围为框架与餐厅扩展源码、Defs、资源引用及控制流。未启动 RimWorld，未运行调试样板店，未建立测试工程；编译后按用户要求部署至 Steam 游戏的 Mods 目录。以下核查不代表游戏内行为已经实测。

## 编译与资源

使用本机 MSBuild 编译餐厅工程，项目引用先构建框架，再构建餐厅 DLL。全部源码已纳入显式 Compile 清单，没有重复或失效引用。检查了 10 种经营家具、33 条扩展 Def 和 4 个商品配置；贴图、方向图、染色蒙版、图标及柜体商品引用均存在。旋转寿司台没有加载建筑 Def。ThingDef 名称按原版 `ThingDef.ConfigErrors()` 检查，不能以数字结尾；两种餐桌分别使用 Square 与 Rectangular 结尾，自动生成的蓝图及建造框架也遵守此规则。

新增和修改的文本按严格 UTF-8 解码检查，未发现零字节或替代字符。没有旧流程存档迁移代码。

## 库存与家具控制流

| 场景 | 源码核查要点 |
|---|---|
| 通断电与腐坏 | CompRottable 前置处理只在实际持有者为通电冰箱时跳过腐坏，不改写腐坏进度，也不拦截其他组件 |
| 冰箱开关按钮 | XML 使用 CompProperties_Flickable，提供原版 CompFlickable 所需的图标和文本字段；不能用通用 CompProperties 只指定 compClass 代替 |
| 容量、目标与在途 | 共享容量和补货租约复用框架，管理窗口保存前验证目标合计；未启用品种没有自动目标 |
| 筛选或区域变化 | 尚未取出的失效预留取消并释放；已到厨师或灶台的食材保留制作归属 |
| 冰箱不足、不可达 | 同一查询先冰箱后绑定储存区，同级按距离；选择完整可工作的厨师路线后冻结实物 |
| 多店共享货源 | 地图级实物预留统一扣除数量，并避让原版预约和在途下架；临时禁用标记在释放时恢复 |
| 地面食材提取 | 原版 Map 也会持有 ThingOwner，先按 Spawned 区分地面与柜内物资；地面使用 SplitOff 后入库，成功后把预留移到实际拆出物，部分提取失败时合回原堆 |
| 掉落餐品恢复 | 地面餐品和商品先 DeSpawn，再交入携带容器；容器间转移仅用于未生成实物，终止订单时已落地商品只解除禁用，不再从地图容器重复丢出 |
| 双人卡座 | 两个占用格独立选择，原版 multiSittable 按格预约，会话与托盘分别归属顾客 |
| 壁挂柜 | 原版墙前逻辑格与依附机制，四向反向材质、贴墙偏移及柜前交互 |
| 拼接吧台 | 只连接相同 Def，摆放或移除时刷新邻接图集，独立图标用于建造菜单 |

## 样板生成与手动到客

样板后厨格位通过原版 GetThingList 排除所有 Building，占用格判断不依赖仅包含主体建筑的 GetEdifice。投放食材和划分后厨使用同一份格位清单，酒柜与橱柜保持在商店内。必须设施、实物缺失和入库数量不符会返回明确失败原因。

强制刷新先同步餐厅经营状态，再重建框架到客快照；所有商店均被排除时，显示动作不可用、人数上限、客群匹配或声望限制。刷新范围仍为当前地图，成功后沿用原有生成结果提示。

## 会话、实物与账单控制流

| 场景 | 源码核查要点 |
|---|---|
| 首单或追加 | 同一框架动作保存会话，一次只有一个未确认请求，成功交谈后冻结子订单并弹一次图标 |
| 等待或进食追加 | 周期推进独立于进食 Job，按已承诺金额及预期营养判断需求，上限和间隔按单店配置 |
| 多员工与首单受阻 | 状态认领互斥，先过滤完整可执行路线，再按接单时间取最早订单；配送优先于接待 |
| 取餐设施预约 | 出餐台和商品柜统一使用 maxPawns=10、stackCount=0；地面餐品使用单人整堆预约，派工检查与实际预约参数一致 |
| 制作中断 | 释放未消耗原料和认领，禁用标记由库存预留统一恢复；已生成餐品只恢复运输，不重复出餐 |
| 厨师连续启动工作 | 预约或执行失败先登记员工与订单的 120 Tick 重试时点，再释放认领；同一员工不会连续认领多张坏单，其他员工和订单继续派工 |
| 取料数量与恢复 | 出发和到达时核对队列、预留、实际数量与携带容量，按货柜策略统一寻路和到达校验；手持当前批次直接运往灶台，落地后清空批次目标 |
| 灶台多批食材 | 每批在灶台五格范围内选无物品的可达格独立生成并登记物理交互预约；不向已满格强制生成，避免原版挪堆和合堆破坏预留引用 |
| 缺损预留核验 | 库存查询保留账面数量，交给业务核验实际数量；不通过 ThingCount 默认构造器截断数量，失败原因包含物品、预留数和实物数 |
| 空闲浏览站位 | 框架浏览在派工与预约时共用站位检查，避让冥想者、顾客及工作台交互预约；无可用站位时结束最低浏览，不重复使用被占用的入口 |
| 多路商品送达 | 厨房菜经出餐台，现货由柜直接取出，整单交入本人托盘，不跨订单合堆 |
| 顾客恢复用餐 | 保存当前子订单、托盘和携带引用；原座从本人容器取餐，已消耗堆叠移出引用集合 |
| 服务超时 | 不重置既有期限，停止追加并取消未交付订单；已送达的可用商品继续处理 |
| 设施或实物丢失 | 周期检查和关键交接即时校验，记录具体原因，释放预留与现存物品 |
| 部分失败 | 按实际吃喝或接受数量收费，保存已消耗成本；零接受会话直接结束，不滞留收银 |
| 重复记账与回调 | 动作与子订单标识幂等登记，冻结明细禁止改价；付款成功回调只处理尚未完成会话 |
| 付款失败 | 不写收入，恢复仍存在的未付款带走实物；不创建已被吃掉的东西 |
| 切页和关闭窗口 | 页面草稿属于窗口上下文，菜单及参数子窗口确认只更新父草稿；货柜独立保存，关闭丢弃 |

存读档路径核查覆盖库存预留、厨师取料队列、服务员携带、私人托盘、进食当前子订单、多张等待订单、账单标记及带走商品直接引用。游戏内的贴墙视觉、缩放布局和人员实际寻路仍需在加载 Mod 后观察。

## 厨师递归派工日志

`红字 (1).txt` 记录的是 `RestaurantIngredientToils.Collect` 在到达食材后结束 Job，随后 `ReleaseClaim` 立即把订单退回待制作，原版 `EndCurrentJob` 同步寻找新工作，最终触发同一 Tick 启动超过 10 个 Job 的保护。重复堆栈属于这条递归调用链。

原日志未包含取料失败分支的具体条件，无法单凭它区分携带冲突、数量或预留失效。当前取料失败会保留订单、工作编号、位置、批次数量和拒绝原因；框架库存接口支持返回未预留、数量不符、容器空间不足及转移失败详情。核查依据为本机原版 `Pawn_JobTracker`、`Pawn_CarryTracker`、`ThingOwner`、`Thing.SplitOff`、`GenPath` 和 `ReachabilityImmediate` 源码，未执行游戏内复现。

## 运行后浏览预约与食材引用日志

2026-09-08 10:21:10 的本机 `Player.log` 中，订单 7、10、20 出现 `ThingCount` 账面数量大于实际 0 件的警告，继而因预留实物失效取消。框架顾客 Ryall、Lynx 共十次尝试预约被冥想者或另一顾客占用的浏览格，导致 `TryMakePreToilReservations` 连续失败。日志还记录六张子订单收银等待超时；该条目本身不足以判断收银员离岗还是排队异常。

源码中存在把每批原料强制 `GenSpawn.Spawn` 到厨师同一格的路径。原版 `GenSpawn` 在物品格已满时会把旧堆移走，随后 `GenPlace` 可把它合入其他堆，使旧引用数量归零。这条路径与日志中的缺损表现吻合，但日志没有记录每个物品的完整移动历史，不能逐件认定其合堆位置。当前放置流程避开已有物品格并保留批次身份，库存快照保留原始账面数量供失败校验。核查依据为原版 `GenSpawn`、`GenPlace`、`ThingCount`、`ReservationUtility`、`PhysicalInteractionReservationManager` 源码，仅完成静态核查与编译，不代表游戏内复现通过。
